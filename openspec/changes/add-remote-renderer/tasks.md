## 4. Renderer transport

- [x] 4.1 Add a `ServerTarget` store in `frontend/src/renderer/lib/server-target.ts` holding `{ baseUrl, label, requiresAuth }` plus the credential, with `setApiBaseUrl` in `api-client.ts` reduced to the supervisor's entry point into it; verify with unit tests that a target change propagates through `subscribeApiBaseUrl` and that the credential is withheld from a target requiring no auth.
- [x] 4.2 Attach `Authorization: Bearer` from the store inside `runtimeFetch` rather than as an `openapi-fetch` middleware: the rebase already reconstructs the request field by field to work around Electron's missing `duplex` getter, and a middleware would either duplicate that reconstruction or be undone by it; verify with `api-client.test.ts` cases asserting the header is present after a credential is set and absent when the target requires no auth.
- [x] 4.3 Offer the credential as the `ao.auth.*` subprotocol in `frontend/src/renderer/lib/terminal-mux.ts` when the target requires auth; verify with a unit test asserting the constructed `WebSocket` receives the encoded subprotocol argument.
- [x] 4.4 On target change, close open mux sockets and drop the react-query cache. The pool grew a `reset()` because nothing else could retire a socket that is still open and healthy to a server the operator has left, and `TerminalCacheProvider` calls it from the target subscription. The cache is cleared rather than invalidated: ids and paths are not comparable across machines, so the old server's answers are wrong rather than stale and must not stay on screen while the new one replies. Re-running the handshake is left to 7.4 — there is no handshake to re-run until the connection screen exists. Verify with `terminal-mux.test.ts` cases asserting a reset reports the drop to every lease and redials, and that resetting an idle pool is a no-op.
- [x] 4.5 Discard the stored credential when the server answers 401, keeping the target so what the operator is asked for next is a password and not an address they already gave (the prompt itself is 7.1); verify with a test asserting a second request after a 401 carries no credential and still goes to the same server.
- [x] 4.6 Replace `EventSource` with a `fetch`-based SSE reader that carries the credential as a header, since `EventSource` can present none and the spec forbids a token in the URL (see design D5a). The reader lives in a new `frontend/src/renderer/lib/sse.ts` rather than inside `event-transport.ts`, because the renderer opens three SSE streams and not one: change events, notifications, and the per-session workspace file watch. All three were on `EventSource`, so all three were converted — a remote client that received sessions but never notifications or file changes would have been a worse bug than one that received nothing. Verify with `sse.test.ts` cases covering multi-line `data:` joins, dispatch by `event:` name, comment heartbeats, and the line terminators the spec allows (LF, CRLF, and a bare CR).
- [x] 4.7 Carry over what `EventSource` provided for free: resume from the last seen `id:` and reconnect with backoff on a dropped or errored stream. Resume sends `Last-Event-ID`, not `?after=<seq>` — the daemon's `parseEventsAfter` already accepts either, and the header is what a reader replacing `EventSource` should be sending, since it is the form every other SSE client and any proxy in between will recognize. Backoff climbs a fixed ladder (1s, 2s, 5s, 10s, 30s) with ±20% jitter so a daemon restart does not bring every open client back in the same millisecond. Verify with `sse.test.ts` cases that a drop mid-stream reconnects carrying the last id, that repeated failures climb the ladder rather than spin, and that an abort is not counted as a failure.
- [x] 4.8 Keep each transport's existing contract intact — `disconnected` on drop, `connected` on open, a workspace refetch on every (re)open, the workspace watcher's degrade-after-three-failures badge. The claim that the suites would pass "with no assertion changes beyond the constructor stub" did not survive contact: the assertions are the same behaviors, but reading a stream is asynchronous where `EventSource`'s stub dispatch was synchronous, so the cases became async and now assert against recorded `fetch` attempts instead of stub instances. Verify the rewritten `event-transport.test.ts`, `notifications.test.ts`, and `workspace-file-events.test.ts` suites pass with their original behavioral coverage intact.

## 6. Renderer capability model

- [x] 6.1 Declare the four host capabilities (`editorHandoff`, `revealInFileManager`, `directoryPicker`, `browserPanel`) as a shared type in `frontend/src/shared/host-capabilities.ts`, reported all-true by the Electron preload and all-false by the browser fallback stub in `lib/bridge.ts`; verified in `lib/bridge.test.ts`. `revealInFileManager` is a separate capability but not a separate bridge method: revealing a folder is the `file-manager` target of the editor handoff, resolved in `src/main/editor-handoff.ts`. Splitting them is what lets a future host offer one without the other.
- [x] 6.2 Add a `useHostCapability(name)` hook as the only permitted read of `capabilities`, folding in the server target (see 6.1 note in design.md D9). Enforced by a test rather than a lint rule — biome only covers `src/landing/**` here, and the check is a scan of `src/renderer/**` for `capabilities[`/`capabilities.` with a single allowed file, plus a vacuity guard so an empty scan cannot pass.
- [x] 6.3 Convert every call site of the four host-bound features to gate on the hook. `editorHandoff`/`revealInFileManager` gate `useEditorHandoffState` and `TopbarOpenEditorButton` (the whole action withdraws, per-target, with the reason on the tooltip); `browserPanel` replaces the `window.ao?.browser` probe behind `hasNativeBrowser` in `useBrowserView`/`BrowserPanel`, so a withdrawn panel falls back to the static preview it already had; `directoryPicker` is not a separate disabled state but is folded into the replacement in 6.5, because a picker with nothing behind it is worse than a field that works.
- [x] 6.4 Make the browser fallback stub throw rather than silently resolve for every method behind a false capability, naming the method and saying the call site should have checked. Two deliberate exceptions, both about *when* the renderer reaches them: `browser.nativeCompositionEnabled` is a value read to choose a render path and has to yield one, and the `browser.on*` subscriptions are registered unconditionally in mount effects, where throwing would take out the panel to prevent nothing. Verified in `lib/bridge.test.ts` by deriving each capability's surface from namespace prefixes, so a new method with a nothing-stub fails until it throws or is written into the exceptions with a reason.
- [x] 6.5 Replace the native directory picker with a path-entry field when the target is remote, in both `CreateProjectFlow`'s folder dialog and `CloneRepositoryDialog`'s destination. The local folder scan and the ancestor-repo check go with the picker — both read this machine's disk, and the project is not on it — which leaves the daemon as the only validator. That required a backend change: `project.Manager.Add` returned `NOT_A_GIT_REPO` for a path that simply was not there, which reads as "wrong kind of folder" when the truth is "no such folder", so it now checks the path exists first and returns `INVALID_PATH`. Verified in `CreateProjectFlow.test.tsx`, `CloneRepositoryDialog.test.tsx`, and `backend/internal/service/project/service_test.go`.

## 7. Renderer connection experience

- [x] 7.1 Added a connection screen that takes an address and password and probes the server before committing to it. The probe is an authenticated `GET /healthz`, not the web-session route, because that route only exists in a daemon built with the web client; `/healthz` is always there and already answers the two questions that matter — is anything listening, and does it accept this password. It distinguishes unreachable, rejected, locked out, and reached-something-that-is-not-a-daemon, and leaves the address in the field on every one of them. Verified in `lib/connect-server.test.ts` (all four outcomes plus timeout and normalization) and `components/ConnectServerScreen.test.tsx` (21 cases, including that a rejected password does not clear the address).
- [x] 7.2 Named the connected server in the sidebar and in the collapsed rail, and marked it reconnecting when the link drops. The indicator watches the change stream rather than the terminal mux: a mux exists only while a terminal is open, whereas every client holds the change stream, so it is the connection whose state is worth reporting app-wide. A dropped mux is the terminal's own business and stays reported there — `hooks/useTerminalSession.test.tsx` drops the socket and asserts the pane says it is reattaching rather than leaving dead output looking live. Stream-level behavior is verified in `components/ServerConnectionRow.test.tsx`, and `lib/event-transport.test.ts` covers the case that made this worth writing down: moving to another server clears the old one's outage instead of reporting it against a machine that has not been tried yet. The indicator renders only for a remote target; a local daemon already has its own failure banner.
- [x] 7.3 Persisted server entries and credentials through the bridge, split across two files because they are not the same kind of secret: addresses go to `remote-servers.json` in plaintext and passwords to `remote-credentials.bin` through `safeStorage`, held in memory only when the platform has no real protection (the same check `cloud-auth.ts` makes on Linux). Removing a server deletes its credential in the same operation, which is why the address is the entry's identity — there is no id for the two stores to disagree about. Verified in `src/main/remote-servers.test.ts` for the persisting host (including concurrent writes and a corrupt file) and in `lib/bridge.test.ts` plus `stores/remote-servers-store.test.ts` for the browser, which persists nothing and says so rather than throwing: its session cookie already survives a reload, so it has nothing to keep.
- [x] 7.4 Reported a version mismatch with both versions once the client learns the server's, taking the daemon's version from the `/healthz` body the probe already reads. It is a note next to the server name, not a gate: an old client against a new daemon is usually fine, and refusing to connect over a string comparison would be worse than the mismatch. Comparison is exact equality rather than semver, since these ship as a pair. Verified in `lib/version-compat.test.ts` and in the mismatch cases of `components/ServerConnectionRow.test.tsx`.
