## 1. Profile resolution

- [x] 1.1 Added `frontend/src/main/launch-profile.ts` with `LAUNCH_PROFILE_ENV = "AO_PROFILE"`, `LAUNCH_PROFILE_ARG_PREFIX = "--ao-profile="`, and a pure `resolveLaunchProfile(argv, env)` returning the validated name or `null`. argv wins over the environment, which is not a style preference: a second copy of a packaged macOS app starts through `open -n -a <app> --args ...`, and LaunchServices does not hand the calling shell's environment to what it launches. An environment-only design would have worked in dev and failed in exactly the case profiles exist for. `launch-profile.test.ts` covers argv-only, env-only, argv-beats-env, neither, and an empty value in either position.
- [x] 1.2 Validated against `^[a-z0-9][a-z0-9._-]{0,31}$`, with cases for `../evil`, `/abs`, `a/b`, `VM2`, a 33-character name, an empty string, and leading `-` or `.` all resolving to `null`, and `vm2`, `vm-2`, `vm_2`, `vm.2` accepted verbatim. The task asked for a separate rejection of the literals `.` and `..`; no such check exists, because the anchored leading character class already makes both unrepresentable. Tests assert the two literals anyway, so the guarantee is covered even though the mechanism is the pattern rather than a branch. Lowercase-only is deliberate and recorded in the source: on a case-insensitive volume `VM2` and `vm2` would be one directory under two names, and whether they collided would depend on the filesystem.
- [x] 1.3 No bootstrap-slot skip was needed, contrary to the task. `open-folder-arg.ts` skips Electron's argv slot because it reads *positional* entries, where the app path is ambiguous with a dropped folder. This matches a flag prefix, and an app path can never start with `--ao-profile=`. The verification the task asked for is still there: a dev-shaped argv and a packaged-shaped argv resolve the same profile, which is the property the skip was meant to produce.
- [x] 1.4 `launchProfileUserDataPath(profile, { home, packaged })` returns the existing `~/.ao/electron` and `~/.ao/dev/electron` for the default profile and `~/.ao/profiles/<name>` / `~/.ao/dev/profiles/<name>` otherwise. Tests assert all four, and assert the two default paths against the literal strings `main.ts` built before this change, so a rename of the helper cannot quietly move an existing install. The dev/packaged split is preserved inside the profile path for the reason it exists at the top level: a dev run and a packaged run of the same profile name are still two Chromium instances and still must not share a profile.

## 2. userData and the single-instance lock

- [x] 2.1 Replaced the literal `app.setPath("userData", ...)` with the helper, extending the surrounding comment to record the profile as a third instance of the same rule the dev/packaged split already follows. A source assertion in `launch-profile.test.ts` fails if `main.ts` stops calling the helper or reacquires the literal path.
- [x] 2.2 The profile resolves once into a module-level `const launchProfile` above the `setPath` call; the title, the tray tooltip, and the remote-mode filename all read that binding. A source assertion holds `resolveLaunchProfile` to exactly one occurrence in `main.ts`, which is what stops the window from claiming one profile while the pinned directory is another.
- [x] 2.3 No code change, as expected. `app.requestSingleInstanceLock()` is untouched. The claim it rests on was verified empirically rather than assumed: a three-process Electron 33.4.11 probe took the lock on directory A (`true`), was refused a second lock on A (`false`), and was granted one on directory B (`true`). The lock is `userData`-scoped, so relocating `userData` is the entire mechanism.

## 3. Per-profile remote-mode record

- [x] 3.1 Added `remoteModeFileName(profile)` to `main/remote-mode.ts`, returning the existing `remote-mode.json` for the default profile and `remote-mode.<profile>.json` otherwise, and threaded an optional profile argument through `readRemoteModeSetting` and `writeRemoteModeSetting`. The argument defaults to `null`, so the seven existing call sites and every existing test keep their meaning. Tests assert the default profile still reads and writes the exact historical filename, that a named profile reads and writes its own, and that a write under one profile is invisible to the other.
- [x] 3.2 The temp-file-and-rename write stays inside the state directory so the rename remains atomic. Writing the test the task asked for uncovered a real pre-existing bug rather than confirming the design: the temp name was `.remote-mode-${pid}-${Date.now()}.json`, so two writes from one process inside the same millisecond built the same path and the second `rename` failed with ENOENT. Replaced the timestamp with a module-level monotonic counter, which cannot collide regardless of clock resolution. The concurrent-write case now passes; before the fix it failed.
- [x] 3.3 Both call sites pass `launchProfile` rather than a literal, and `editorStateDir()` is unchanged: the state directory is shared and only the filename is per-profile, which is what keeps the address book in the same place for every profile.
- [x] 3.4 `remote-servers.json` and `remote-credentials.bin` are untouched. The diff mentions neither outside documentation and a doc comment in `remote-mode.ts` recording why the split is per file: what a client *is* differs per profile, what the operator *knows* does not.

## 4. Per-launch server override from argv

- [x] 4.1 `resolveRemoteServer` now takes `(argv, env, persisted)` and recognises `REMOTE_SERVER_ARG_PREFIX = "--ao-server="`, with precedence argv > environment > persisted. Tests cover each level winning over the ones below it.
- [x] 4.2 The empty-value escape hatch works at the new level: `--ao-server=` with no value resolves to `null` even when both the environment and the persisted setting name a server, exactly as an empty `AO_REMOTE_SERVER` does.
- [x] 4.3 An argv override reports `source: "env"`, and the type's doc comment records why. The field drives whether the UI offers the operator a setting to change; a launch flag is no more theirs to change from the UI than an environment variable is, so a third source value would have been a distinction nothing acts on.
- [x] 4.4 The `main.ts` call site passes `process.argv`. All seven existing call sites in the tests moved to the three-argument form and the existing source assertions still hold, with one added for the new argument.

## 5. Labelling concurrent clients

- [x] 5.1 `launchProfileWindowTitle(profile)` returns `Agent Orchestrator` unchanged for the default profile. For a named one the separator is `·`, not the `--` the design specified: `tray.ts` already qualifies a name with the thing it belongs to using `·` (session · project), and inventing a second separator for the same job in the same process would be the inconsistency. One test asserts the default string against the literal `main.ts` carried before the change.
- [x] 5.2 The window `title` calls the helper; a source assertion fails if the literal returns. Whether the option survives `index.html`'s own `<title>` is a real question with a non-obvious answer, checked in 8.1a rather than assumed.
- [x] 5.3 `TrayControllerOptions` gained a required `idleTooltip`, which `main.ts` fills from the same helper. The attention-count tooltip is unchanged and still renders `tray.attentionTooltip` through `tPlural`. Three cases cover the idle tooltip named and unnamed, and a non-zero count still producing the plural string.
- [x] 5.4 Audited every remaining `Agent Orchestrator` literal in the main process. `app.setName` (`main.ts:138`), the About panel (`main.ts:1919-1920`), the relocation and update prose in `main/auto-updater.ts`, and the sign-in errors in `main/cloud-auth.ts` are all the product's name rather than this launch's, and stay. `main/menu.ts` carries no app-name literal, and notification titles come from the renderer per session, not from the app name. `app.getName()` has no callers anywhere in `src/`. The honest limitation this leaves: on macOS the dock tile and the app menu read the same for every profile. They come from the bundle's `CFBundleName` in a packaged app, where `app.setName` does not reach, so making them per-profile would work in dev and silently do nothing where it matters -- the failure mode the argv flag exists to avoid in the first place. The window title and the tray tooltip are what distinguish the clients.

## 6. Launcher

- [x] 6.1 Added `frontend/scripts/launch-profile-helpers.mjs` (pure) and `frontend/scripts/launch-profile.mjs` (thin), the split `build-web-client-helpers.mjs` established. `launchCommand` composes `open -n -a <app> --args --ao-profile=<name> [--ao-server=<url>]` on darwin and a direct exec elsewhere; `knownAppLocations` lists the fallbacks, and the script prefers the `~/.ao/app-state.json` marker the way `ao start`'s `resolveApp()` does, honouring `AO_DATA_DIR`. `launch-profile-helpers.test.mjs` asserts the composed argv per platform. One test reads `src/main/launch-profile.ts` as text, extracts its `VALID_PROFILE` literal, and asserts it equals the `.mjs` copy -- the duplication is unavoidable across the two module systems, and this is what stops the two from drifting into a launcher that accepts what the app rejects.
- [x] 6.2 The launcher exits 2 on a name the app would reject, printing the rule. The app itself still falls back to the default profile, which is the right answer for a process that is already starting and the wrong one for a launcher that can still say no.
- [x] 6.3 Added `npm run launch:profile`, not the `dev:profile` the task named. A package script cannot take a positional name without a wrapper of its own, and the dev path does not need one: `AO_PROFILE=vm2 AO_REMOTE_SERVER=... npm run dev` already works, because a dev run inherits the shell environment. That is precisely the case the argv flags exist to cover and dev does not have. Documented the environment form for dev and shipped the launcher for the packaged path, where it is the only option.
